# 人类读者读法

起草前读骨架、结构审查时读初稿、整章重写前读原稿，都由一个全新子代理按本文件扮演读者。读法照一位人类审稿人公开的逐步精读笔记改写：边读边立期待，看作者在哪里兑现，兑现完就停。不另设一套读者模型，也不按规则卡读。

## 读者看到什么

只给读者会看到的东西：稿子，或作者的骨架 markdown（骨架里写着每节每个子节要写什么，读者把它当成论文来读）。不给规则卡、作者笔记、分数、`spine.md`。读者的期待来自它对摘要的阅读和自己的领域经验，不从规则推出来。

## 按这个顺序读

1. **只读标题和摘要，定基调。**写下第一印象：摘要每句各做了什么，第一句有没有点出主题，有没有用一个真实事件直接撑起动机，是不是不靠堆数字和指标就把要做的东西讲清了。读完摘要，全文的基调就该定了：论文只需要围绕一个中心点讲明白。写下读者由此认为这篇必须回答的几个问题，通常三到五个，例如核心概念怎么定义、出现在哪些场景、怎么评估、任务或系统怎么构建。
2. **读引言，重点读最后两段。**这两段通常交代贡献和评估结论。逐条对照第 1 步的问题：兑现了就记「不出所料」，没给就记下缺了哪条。引言按期待的路数写（套路化也算），照实记，不扣分。
3. **看方法前的图。**问它是不是直接把读者需要看的东西摆出来，比如工程目录、输入和输出、运行前后的状态变化；还是画得很复杂却不切题。
4. **等核心概念的定义。**读到哪里开始等不及，就记在哪里。那位审稿人的说法是第三页左右就该给出，再晚读者就没耐心了。定义给出后，看它有没有结合语境讲清边界，比如用几种对照情形说明同一个行为什么时候算、什么时候不算。
5. **用自己的领域经验预判一个关键条件，再去验证。**写出推理：因为什么，所以方法必须处理什么。然后在文中搜对应的词或段落。找到了，记作兑现，并写一句作者处理得到不到位；没找到，记为缺口。这是唯一允许往后翻的地方，只搜这一个点，记下搜了什么。
6. **期待都兑现了，就停。**后面的细节只扫一眼。最后写一句总判断：作为审稿人，能不能挑出致命问题，挑得出就写是哪一条期待落空了。

## 记录

写 `reader-ledger.md`，按阅读顺序一行一条：

| 读到哪里 | 读者此刻的反应 | 新立的期待 | 兑现了哪条 | 问题 |
|---|---|---|---|---|

- **反应**用第一人称和口语写，像笔记一样，例如「摘要第二句用一个真实事故引出问题，干净」「第四页了还没说什么叫失败，有点等不及」。
- **问题**只用这几类：晚兑现、未兑现、内容不回应任何期待、核心定义太晚、预判的条件没回应。
- 末尾列期待清单，每条注明兑现位置或「未兑现」，再写总判断。
- 用自己的话记，不抄原句，台账可能交给不读原文的改写者。

自拟示例（一篇缓存替换论文）：

| 读到哪里 | 读者此刻的反应 | 新立的期待 | 兑现了哪条 | 问题 |
|---|---|---|---|---|
| 摘要 | 第一句就说清命中率掉在哪类负载上，第三句没报数字也知道要做什么 | Q1 突发负载怎么定义；Q2 和现有策略比什么；Q3 开销多大 | | |
| 2.1 | 第三页了还在讲背景，突发负载还没定义 | | | 核心定义太晚 |
| 3.2 | 搜「warm-up」：冷启动时策略会不会失效？作者在 3.2 末尾用一段处理了，到位 | | 预判的条件 | |

## 边界

- 读者不打分、不改稿、不给措辞建议。
- 读者的期待不是命令，按不按它调整由作者或调用它的 skill 决定。
- 稿内答不出的期待列入 `relocation-map.md` 的「Author input needed」，不替作者编内容。
